# Testing Strategy

## Layers

| Layer | Tooling | Where |
|---|---|---|
| Unit tests | `#[test]` | next to code in each crate |
| Parser golden tests | `insta` snapshots of the parsed model (RON/JSON) | `crates/*/tests/` |
| Diagram golden tests | `insta` snapshots of Mermaid/DOT text | `crates/s5k-render/tests/` |
| Property tests | `proptest`: generate ladder ASTs → text → parse → equal | `crates/s5k-logic/tests/` |
| Fuzzing | `cargo-fuzz` targets: L5X reader, ladder parser, ST parser | `fuzz/` |
| End-to-end CLI | `assert_cmd` + fixtures | `crates/s5k-cli/tests/` |
| Benchmarks | `criterion` on synthetic 1/10/100 MB projects | `benches/`, nightly CI |

## Fixture policy

- **Never commit customer or employer project files**, even "old" ones.
- Fixtures in `tests/fixtures/` are either hand-written minimal L5X files or
  generated by `xtask gen-fixture`, or real files run through `s5k sanitize`
  and reviewed by a person before commit.
- Each fixture has a header comment saying what it exercises and which
  `SoftwareRevision` it imitates.
- Large generated fixtures are not committed; CI generates them.

## Naming

Tests that cover a requirement include its ID: `fr_par_007_partial_routine_export`.

## Definition of done for a change

1. Tests cover the new behaviour (including at least one malformed-input case for parsers).
2. `cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace` pass.
3. Snapshots reviewed (`cargo insta review`), not blindly accepted.
4. Docs updated if behaviour or requirements changed.
